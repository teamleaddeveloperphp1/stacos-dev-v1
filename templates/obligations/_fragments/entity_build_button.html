The label is decided by `has_calendar` (`stacos.obligations.views.entity_preview_context`), not repeated in two places — except inside the guided setup wizard, where `in_setup` overrides it back to the "create" phrasing regardless; see `entity_build_button_label.html`. The button's own colour follows the same `in_setup` override, not `has_calendar` alone — a user revisiting the wizard on an entity that already has a calendar (browser back, a bookmarked step) still reads "Create my calendar" here, and a muted outline button under text that says "create" disagreed with itself, easy to miss beside "Back" in the wizard footer where it is the only forward action on the screen. The steady-state entity page, where this same button can genuinely say "Save changes", is the one place the quieter outline style still applies. The number is the real total the register will hold once a build runs right now — the planner run behind `stacos.obligations.services.preview`, not the count of rules that apply (`preview.applies_count`, shown separately above this button — see `entity_preview_stats.html`). One rule commonly becomes many rows: a GST rule fires once per GST registration, and a monthly rule fires once per month inside the materialisation horizon, so "6 rules" honestly building "64 obligations" is expected, not a bug — see that template's explanatory line for what tells the user so before they click. Deliberately the *total*, not `len(plan.to_create)`: this button also renders for an entity revisiting the guided setup after already having a calendar (browser back, a bookmarked step), where most of what applies is already on file and the planner correctly finds nothing new to create — showing "0 obligations" there would read as broken rather than as "nothing changed". Posting to `compliance:rebuild` either way: the planner never destroys an obligation carrying history, so a "build" on an entity that already has a calendar is exactly as safe as a "rebuild". `finish_setup` tells `rebuild_calendar` to send the browser on to the dashboard once this succeeds, which is what turns this button into the last step of the guided setup flow instead of an in-place refresh with nowhere further to go. Exactly one template sets it: the setup flow's Build step, which renders this button in its wizard footer. It was briefly a flag on the card in the header here, and had to be threaded back through the querystring on every re-render because this card swaps itself out; rendering the button outside the swapped region instead is what removed the need. `button_class` lets that footer ask for a full-size primary button, matching the "Next" button every earlier step of the wizard ends with. The card header wants the small one, so that is the default. The count lives in its own ``#build-button-label`` span so it can be kept current with an out-of-band swap when this button sits outside the region that answering a question or toggling a pack re-renders — see ``stacos.obligations.views._render_entity_preview``.
